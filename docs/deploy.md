# Deploying for free

The live demo runs on two free plans, with no credit card:

- **Render** (free web service): runs the API, which also serves the built web app.
- **MongoDB Atlas** (free cluster): the database.

Every push to `main` deploys by itself once GitHub Actions CI has passed.

On the public site, sign-ups are off and the shared demo accounts can't log in, so nobody can change the restaurants everyone browses. Instead, **Try the demo** gives each visitor a private copy of the demo data, which MongoDB deletes after 24 hours (see [How the demo works](../README.md#how-the-demo-works)).

Free plans change. These steps were written in November 2026.

## 1. The database on MongoDB Atlas

1. Sign up at [mongodb.com/atlas](https://www.mongodb.com/cloud/atlas/register) (Google or GitHub sign-in works).
2. **Create a cluster:** choose the **Free** tier, provider **AWS**, region **N. Virginia (us-east-1)**. That's next to the Render region in `render.yaml`. Name it `foodiez`.
3. **Create a database user** (Security → Database Access): username `foodiez`, a long generated password, role **Read and write to any database**. Copy the password somewhere safe now.
4. **Allow connections** (Security → Network Access): add `0.0.0.0/0` (allow access from anywhere). Render's free plan has no fixed IP addresses to list instead; the generated password and TLS protect the database.
5. **Copy the connection string** (Connect → Drivers). It looks like this. Put the password in, and add the database name `foodiez` after the `/`:

   ```
   mongodb+srv://foodiez:<password>@foodiez.abc123.mongodb.net/foodiez?retryWrites=true&w=majority
   ```

Don't paste it anywhere but Render. You don't need to create any collections: the API creates them, and adds the showcase restaurants on its first start.

## 2. The app on Render

1. Sign up at [render.com](https://render.com) with GitHub, and allow it to see the `foodiez` repository.
2. **New → Blueprint**, then pick the repository. Render reads `render.yaml` and shows one free web service.
3. When it asks for **`MONGODB_URI`**, paste the connection string from step 1. Everything else is set in `render.yaml`, and Render generates `JWT_SECRET` itself.
4. **Apply.** The first build takes a few minutes. When the log shows `Foodiez API listening`, open the service's URL (something like `https://foodiez.onrender.com`).

## 3. Check it

- `https://<your-app>/api/health` returns `{"status":"ok"}`.
- The home page shows the five showcase restaurants, with **Try the demo** above them.
- Press **Try as a customer**: a banner says the demo is private and deleted in about 24 hours. Place an order, press **Switch to the restaurant owner**, change a menu, and switch back to see the change.
- Open the site in a private window: the showcase is unchanged.

## How it stays free

| Plan | Limit | How Foodiez stays inside it |
|---|---|---|
| Render web service | 750 instance-hours a month; sleeps after 15 minutes without requests | One service runs everything. It sleeps when nobody's visiting, and the first visit after that takes about a minute while it starts. |
| MongoDB Atlas free cluster | 512 MB of storage, 500 connections, about 100 operations a second | A demo is about 35 small documents (well under 50 KB). At most 200 exist at once (`DEMO_MAX_ACTIVE`), and each IP can start 10 an hour (`DEMO_RATE_LIMIT`). MongoDB deletes them after 24 hours with TTL indexes, so storage stays flat. Sign-ups are off, so nobody can fill the database. |

If the database gets no connections for several weeks (nobody visits the site), Atlas pauses the free cluster and emails you. Resume it from the Atlas dashboard.

### Don't

- **Don't add an uptime pinger** to keep Render awake. It would use the month's free hours. The minute-long first load is the price of free.
- **Don't turn on `DEMO_ACCOUNTS_LOGIN` or `SIGNUPS_ENABLED`** on the public site. Either lets visitors change what everyone else sees.

## Settings

`render.yaml` sets these. Change them under the service's **Environment** page on Render.

| Name | Value on the demo | Why |
|---|---|---|
| `MONGODB_URI` | your Atlas string | Set by you in step 2 |
| `JWT_SECRET` | generated by Render | Signs login tokens |
| `WEB_APP_DIR` | `frontend/dist` | The API serves the built web app, so it's one service |
| `TRUST_PROXY` | `1` | Render's proxy sits in front, and rate limits need the real visitor IP |
| `SEED_DEMO_DATA` | `true` | Adds the showcase restaurants on the first start |
| `DEMO_ACCOUNTS_LOGIN` | `false` | Locks the shared demo accounts |
| `SIGNUPS_ENABLED` | `false` | Visitors use private demos instead |

The rest (`DEMO_TTL_HOURS`, `DEMO_MAX_ACTIVE`, `DEMO_RATE_LIMIT`) keep their defaults; see [`backend/.env.example`](../backend/.env.example).

## Troubleshooting

| What you see | What to do |
|---|---|
| The deploy log says `Could not connect to MongoDB` | Check the connection string: the password is filled in, `/foodiez` comes before the `?`, and Network Access allows `0.0.0.0/0`. If the password has symbols like `@` or `/`, URL-encode them or generate one without. |
| The deploy log says `MONGODB_URI is required` | The variable wasn't set in step 2. Add it on the service's **Environment** page. |
| The page takes a minute to load | The free service was asleep. That's expected. |
| "The demo is very popular right now" | 200 demos are active. They expire after 24 hours, or raise `DEMO_MAX_ACTIVE`. |
